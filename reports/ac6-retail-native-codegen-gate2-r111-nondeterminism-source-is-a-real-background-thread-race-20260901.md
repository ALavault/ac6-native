# AC6 retail NTSC-U/J — r110's nondeterminism is a real background-thread race: `ExCreateThread` spawns a genuine host thread that SIGSEGVs in guest code (r111)

Date: 2026-09-01.

## Checkpoint sweep across GATE1-5, then catching the crash directly

Instrumented all 46 call sites between `sub_821D5F48`'s prologue and
its post-GATE2 `loc_821D6358` loop (the same region r105 originally
named GATE1 through GATE5) with numbered markers, gated by
`AC6_R111_DIAG`. Six runs of the identical instrumented binary again
diverged -- but this time two runs **segfaulted** (`exit=139`) rather
than merely timing out, both stopping around checkpoint 28-29 (`cp29`
= immediately after `sub_82338300`, r105's own GATE1 check).

**Caught the crash directly rather than inferring it from missing
checkpoints.** This is a different use of GDB than the live
breakpoint-stepping r103/r104 found unreliable for this probe: running
to completion under `gdb --batch -ex run -ex bt` and letting the
debugger record whichever signal the process actually raises is a
standard, passive technique, not interactive single-stepping. Two of
four such runs reproduced the segfault and printed an identical
backtrace both times:

```
[New Thread 0x7ffee7fff6c0 (LWP 1134058)]
...
Thread 15 "ac6recomp" received signal SIGSEGV, Segmentation fault.
[Switching to Thread 0x7ffeee7146c0 (LWP 1134054)]
0x0000555555ed716e in __imp__sub_82346428 ()
#0  0x0000555555ed716e in __imp__sub_82346428 ()
#1  0x0000555555ed4e70 in __imp__sub_823453E8 ()
#2  0x00005555557a0b0e in __imp__sub_821F8008 ()
#3  0x00007ffff74f5ef9 in ?? () from /usr/lib/x86_64-linux-gnu/libstdc++.so.6
#4  0x00007ffff70a407a in start_thread (arg=<optimized out>) at ./nptl/pthread_create.c:454
#5  0x00007ffff713772c in __GI___clone3 () at ../sysdeps/unix/sysv/linux/x86_64/clone3.S:78
```

**This crash is not on the main probe thread at all.** `[New Thread
...]` and the `start_thread`/`__clone3` frames at the bottom of the
backtrace show a genuinely separate, real OS thread, distinct from the
main thread whose GATE1-5 checkpoints were printing in parallel. Every
run's main-thread checkpoint trail (`cp12`..`cp29`, or `cp1`..`cp46`
followed by a clean timeout) is a different, coincidental snapshot of
*where the main thread happened to be* at the moment this unrelated
background thread's crash killed the whole process -- not evidence
about the main thread's own control flow diverging. This resolves
r110's finding without contradicting it: the *main-thread* stall
timing genuinely does vary run to run, but the cause is a race with
this second thread, not nondeterminism inside `sub_821D5F48` itself.

## The thread is real, not a probe artifact

Grepped for how `ExCreateThread` is implemented
(`tools/materialize_native_import_stubs.py` lines 271-301): it copies
the calling `PPCContext`, gives the copy a fresh 64KiB stack slice
(`g_next_thread_stack.fetch_sub(0x10000u)`), and launches it via
`std::thread([shim, worker, base]() mutable { shim(worker, base); }).detach()`
-- a genuine host OS thread running real guest PPC code concurrently
with the main thread, not a synthetic or no-op stub. (An earlier
session's summary description of thread-creation stubs as writing "a
guest handle without a host thread" describes a different stub or a
stale understanding -- `ExCreateThread` specifically does spawn a real
thread, confirmed by reading its current implementation directly.)

## Decision

This is a real, load-bearing finding, not a diagnostic reversion: the
"nondeterminism" r110 documented is a genuine data race between two
real host threads, one of which (spawned via `ExCreateThread`, running
guest code starting from `sub_821F8008` -> `sub_823453E8` ->
`sub_82346428`) crashes with a SIGSEGV inside `sub_82346428` on a
substantial fraction of runs. This is not yet root-caused to a specific
instruction or guest-memory access -- the crash offset
(`__imp__sub_82346428+414`) and its actual cause (null pointer, stack
overflow against the thread's 64KiB slice, or a genuinely uninitialized
value analogous to r108's `MmQueryStatistics` finding) are unestablished
this cycle. Guessing which is refused, per this project's standard for
a plausible-but-unverified claim.

No native code changed. This cycle's contribution is narrowing five
runs' worth of apparently-erratic main-thread behavior down to one
concrete, reproducible crash site on a specific, real background
thread.
