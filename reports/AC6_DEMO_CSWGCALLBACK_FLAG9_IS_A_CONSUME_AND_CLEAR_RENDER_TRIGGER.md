# `CSwgCallback+9` is a consume-and-clear trigger that also gates the swg renderer's per-frame draw call

## Qualification

AC6 demo PAL, same XEX SHA-256. Static evidence:
`codegen/generated/ppc_recomp.{4,15}.cpp` (control-flow evidence only). Live
evidence: a new watched run (`AC6_DEMO_WATCH_ADDR_LO`/`HI` on the mode
manager's `request` field, `probe --until frontend --max-ticks 3600`, START
at tick 3000). No oracle.

## What prompted this

`956bd743` closed "does anything reachable arm `CSwgCallback+9`" with no.
This reads `0x820CE368` (the function that checks it) in full for the first
time — previously only its opening null-check and the general shape ("skips
its frame step") were known from an inherited trace comment.

## What `0x820CE368` actually does

After the already-known `[CSwgManager+4]` and `[+236]`/`[+224]`
(`world`/`anim`/`player`) null-checks, it makes two virtual calls
(`player.vtable+8`, `player.vtable+52`) building up return values, **then**:

```powerpc
lbz  r11,9(r26)        ; r26 = anim (CSwgCallback instance)
cmplwi r11,0
beq  0x820ce4f4         ; flag == 0 -> skip the whole block below
```

The block this skips, when the flag is nonzero:
- conditionally recomputes `[player+4136]` (a modulus/period value, via a
  `divw`-based check gated on `[player+4124]==1`);
- increments the frame counter `[player+4132]`, wrapping it against
  `[player+4136]`;
- calls `player.vtable+68` with `[player+4124]` and `[player+4128]` as
  arguments — the shape of a "draw frame N" call, on the object whose own
  vtable (`0x82007D0C`) is `CSwgRenderer`'s;
- **then unconditionally writes `[anim+9] = 0`** — the same byte it just
  read, cleared back to disarmed.

This is a **consume-and-clear** pattern: something else is meant to pulse
this byte high once per intended frame advance, `0x820CE368` consumes it,
advances the frame, calls the renderer, and clears it for the next pulse.
It is not a one-time "system ready" latch — `956bd743`'s conclusion (no
reachable arming path) still holds, but the *consequence* of that dead flag
is now known precisely: **the swg renderer's own per-frame draw call
(`player.vtable+68`) never executes, at all, for the entire run.** This is
independent of, and additional to, the ring/doorbell finding
(`4fe5d5b2`) — even content that *would* reach the ring never gets
generated by this path in the first place.

## A second question this answers: title's state does NOT come from here

`0x820CE368` makes exactly six stores (checked in full): the stack frame,
one unrelated global at a fixed negative offset, the two frame-counter
fields, and the flag reset. **None of them write the title's own state
field** (`[title_this+12]`, which would be `[this_arg-16]` from this
function's own parameter). This rules out the hypothesis (raised while
tracing this) that `0x820CE368` itself is what advances the title's state
machine from 1 to 2 once the swg step "completes" — it doesn't, even in
the case where the flag is set. **Whatever would advance title state 1 to
2, it is not this function; not located.**

## Live confirmation that title's state-transition request only ever fires once

Watching `[manager+24]` (the "request" field the title's state-2 handler
writes, per `20fb6c48`'s original code comment) across the full 3600-tick
run: four writes total (poison, zero-init, `value=1`, `value=0`), all
during the single observed `startup -> title` transition at tick ~222.
**Zero further writes for the rest of the run, including after the
correctly-timed START press at tick 3000.** Consistent with, but not
proof of, the state machine being stuck: title's own state (`[title_this+12]`,
traced via `AC6_MODE_INNER`) is confirmed frozen at `1` for the whole run
(no new trace needed — the existing `AC6_DEMO_WATCH_MODE_STATE` output
already showed this, unchanged since this session's earlier runs).

## Conclusion

Two independent, now fully-diagnosed dead ends converge on the same root:
title's state machine has a countdown-then-request state (state 2) that is
never reached because state 1 never completes, and separately, the swg
renderer's own frame-advance call is permanently skipped by the same dead
`CSwgCallback+9` flag that state 1 polls. Neither `0x820CE368` nor state
1's own handler contains a path that could advance the title past state 1
by itself — the actual trigger, wherever it lives, was not found here.

## Not established

- What is meant to set `CSwgCallback+9` to nonzero — `956bd743` ruled out
  the three literal-`1` reachable candidates; the mechanism (if any is
  reachable at all) remains unfound.
- What (if anything) is meant to advance `[title_this+12]` from 1 to 2 —
  a message/event listener is the leading hypothesis (per the two
  registered listeners already traced, `AC6_MSGLISTENERS`, one with vtable
  `0x82011384`), not traced further here.
- Whether `player.vtable+68`'s draw call, if it ran, would visibly change
  anything — not established; only that it never runs.
