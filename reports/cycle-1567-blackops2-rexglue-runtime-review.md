# Cycle 1567 — audit Black Ops II / ReXGlue pour le runtime AC6

Date de l'état public vérifié : **2026-08-12**. Cible de comparaison : AC6 PAL
Xbox 360, Mission 01. Aucun contenu retail n'a été téléchargé ou lu et aucun
binaire de jeu/recompilé n'a été exécuté.

## Verdict

La recherche publique (`"Black Ops II" recompiled`, `bo2 recompiled xbox 360`,
`default_mp.xex rexglue`, variantes BO2/T6/ReXGlue) ne laisse qu'un projet de
recompilation substantiel : `officialmelon/bo2-recompiled`. Il n'a ni fork
public, ni tag, ni release, ni PR, ni workflow GitHub Actions, ni licence de
projet. Deux états doivent être distingués :

| État | Pin exact | Inventaire | Verdict |
|---|---|---:|---|
| branche par défaut `main` | [`7ba8bb3ce0b45c5c1a63884510810679490bd512`][bo2-main-commit], arbre `ff30dae4dd16526470afc530450a7c611c3c1b92`, 2026-04-10 | 17 commits, 21 chemins, 59 243 octets | petit lanceur ReXGlue, SDK et code généré non verrouillés |
| branche publique `codex/native-renderer-wip` | [`c096a06b1fee4925482e37870c2e54c82e3fd9b6`][bo2-wip-commit], arbre `260c7347c2efbef0edce20e5e4614a3b0d30322f`, 2026-07-05 | 235 commits, 175 chemins, 2 649 837 octets ; 218 commits après `main` | instrumentation ambitieuse mais non reconstructible avec les entrées publiques |

Résultat taxonomique : **aucun élément `retail-qualified`**. La seule idée à
reprendre pour AC6 est l'architecture d'une trace ordonnée au bord du command
processor/VdSwap, complétée par des compteurs explicites de pertes et de
fallback ; elle reste `provisional-rexglue`. L'injection d'entrée, la cadence
native et le renderer D3D12 partiel sont `divergent`. Les affirmations de jeu,
les captures privées, XMA/vidéo, contenu/sauvegardes et Linux sont
`documented-unmatched`.

## Qualification du jeu et des affirmations

Le README dit « playable state », cible `default.xex` et `default_mp.xex`, et
ne donne que le nom et le SHA-1 d'une ISO « World »
([lignes 1–43][bo2-readme]). Il ne donne pas les SHA-256 des deux XEX, Title ID,
Media ID, région précise, TU/DLC, ni un manifeste des fichiers extraits. Le
runtime attend un répertoire `assets/`, explicitement ignoré par Git
([README lignes 45–88][bo2-readme-platforms], [.gitignore][bo2-gitignore]). Le
code généré est lui aussi ignoré. Il est donc impossible de relier les adresses
et hooks à une image exécutable qualifiée, et a fortiori à AC6 PAL.

Les messages historiques annoncent boot menu/MP/Zombies et le README annonce
la jouabilité, mais il n'existe dans l'arbre public ni journal qualifié, ni
capture d'entrée/état, ni vidéo, ni fixture retail bornée, ni exécutable publié.
Ce sont des affirmations **`documented-unmatched`**, pas une preuve de gameplay.
Le dépôt ne suit aucun XEX/ISO/fastfile/capture retail ; la branche WIP suit
toutefois 27 DXBC et 20 HLSL dans `shader_work/`, sans manifeste de provenance
ou licence. Ces dérivés ne sont pas une qualification et leur réutilisation est
exclue.

## ReXGlue, codegen et dépendances exactes

### ReXGlue n'est pas reproductible publiquement

`main` demande un SDK externe par `REXSDK_DIR` et un CLI `rexglue` trouvé dans
`PATH` ([README lignes 56–81][bo2-readme-platforms]). Aucun submodule, lock ou
SHA ReXGlue n'est déclaré ; `generated/rexglue.cmake` n'est pas suivi.

La branche WIP ajoute un manifeste portant `sdk_version = "0.8.0.0"`
([manifest SP][bo2-manifest-sp]), compatible nominalement avec le tag public
ReXGlue v0.8.0 [`2bdb97f95f154f32d281aaa08446ae007b8ca117`][rex-v080]. Ce champ est
un tampon « project last generated by », pas une contrainte de checkout
([implémentation v0.8.0][rex-sdk-stamp]). Les scripts continuent en outre à
appeler `rexglue codegen default_config.toml` et l'équivalent MP
([script Linux][bo2-codegen]). Or ces fichiers WIP ne contiennent plus
`project_name` ni `file_path`. Le code public v0.8.0 tente alors une conversion
legacy et échoue sur ces champs avant de pouvoir utiliser le manifeste existant
([sélection/chargement du manifeste][rex-codegen-discovery],
[branche legacy][rex-codegen-legacy]). Une régénération froide suivant les
scripts versionnés n'est donc pas définie.

Le WIP appelle en plus `NativeRenderer*Event`,
`NativeRendererTraceCallbacks` et
`CommandProcessor::SetNativeRendererTraceCallbacks`
([enregistrement du sink][bo2-trace-callbacks]). Un `git grep` exhaustif de ces
symboles donne zéro occurrence dans les arbres publics ReXGlue v0.8.0, v0.9.0
[`3eb9b511b4140d2769e27be63eae57d41bfa2afa`][rex-v090], `main`
[`cb58065c793429aa92895d778af58d12e9d26d8f`][rex-main-090] et
`development` du 2026-08-11
[`df2743b069d0db19f8ecad2688eecb14e23e1565`][rex-development]. La documentation
WIP exige des captures après un commit court `3ed291c`, absent du dépôt public
([état de capture][bo2-render-progress]), puis reconnaît des headers installés
obsolètes, une copie manuelle depuis `C:\Users\braxt\rexglue-sdk` et un échec de
link faute du symbole attendu ([journal WIP][bo2-private-sdk]). Le renderer WIP
ne peut donc pas être compilé depuis les seules sources/pins publics observés.
Le SDK public porte un texte permissif à trois clauses de type BSD, bien que
l'API GitHub le classe `NOASSERTION` ([licence ReXGlue v0.8.0][rex-license]) ;
cela ne couvre pas le code propre au dépôt BO2.

## XAM input, polling et replay

Le WIP intercepte `XamInputGetState` à des adresses BO2 codées en dur. Le hook :

- refuse certains flags avec `0x48F`, rabat `AnyUser`/`0xFF` sur l'utilisateur
  zéro, appelle l'input ReXGlue puis restaure son résultat ;
- vide ensuite toute la file clavier dans un callback guest direct, donc le
  regroupement des événements dépend du nombre et de l'ordre des polls
  ([hook complet][bo2-input-poll]) ;
- consomme `mouse_dx/dy` par échange atomique à chaque lecture et combine états
  maintenus, deadzone Android `0.22` et gain de stick droit `18`
  ([snapshot][bo2-input-snapshot]) ;
- borne la file à 256 en supprimant l'événement le plus ancien ; les timestamps
  sont `GetTickCount()` sous Windows et zéro ailleurs
  ([file/timestamps][bo2-input-queue]) ;
- incrémente le `packet_number` Android à chaque poll, même sans changement
  ([mapping Android][bo2-input-android]).

Le second hook appelle le constructeur de commande original, puis OR/écrase
boutons et déplacements et modifie directement pitch/yaw guest. Son trampoline
vérifie une prologue hôte x86-64 fixe de 12 octets. Hors Windows, il ne crée pas
ce trampoline ; hors Android l'installation retourne avant même d'enregistrer
les dispatchers ([détour/commande][bo2-input-detour],
[installation][bo2-input-poll]). Ce n'est ni le contrat XAM retail ni une
solution Linux : **`divergent`**.

Il n'existe aucune trace/relecture d'entrée ni fixture de cadence de poll. Pour
AC6, seule la position du seam est utile : enregistrer à la frontière réelle
`XamInputGetState` l'ordinal d'appel, tick/timebase guest, thread, utilisateur,
flags, HRESULT, `packet_number` et l'état complet ; rejouer sans clavier/souris
native, en conservant les polls multiples par tick, les erreurs et la règle de
packet inchangé. Ne jamais identifier un poll à un `PRESENT`.

## Scheduler, cadence et VdSwap

Le projet ne fournit pas de scheduler déterministe. Le WIP impose
`vsync=false`, 1280×720@60, compilation shaders asynchrone, un thread Vulkan,
`audio_maxqframes=10` et `ignore_thread_priorities=true`
([configuration][bo2-runtime-config]). Le pump UI Android dort 16 ms
([pump][bo2-android-pump]) : c'est une cadence hôte approximative, pas le tick
guest. Le benchmark tue le processus après une durée fixe et calcule seulement
une moyenne entre deux timestamps de log, sans scénario/input fixe ni
percentiles ([benchmark][bo2-fps-benchmark]).

La meilleure observation du dépôt est qu'il faut laisser ReXGlue exécuter le
paquet `XE_SWAP` original : le guest sonde le writeback de fin de swap et, sans
lui, tombe dans un timeout d'environ 300 ms par frame
([VdSwap][bo2-vdswap]). C'est un invariant **documenté mais non accompagné de
capture publique**. Le backend D3D12 présente sa fenêtre avec `Present(0, 0)`
([present natif][bo2-present-zero]), donc ne matérialise pas la cadence retail.

Action AC6 : dans un mode diagnostic seulement, conserver intégralement le
VdSwap/écriture de complétion original ; tracer séparément tick guest, ordinal
de poll input, début/fin swap, valeur/latence de writeback et présentation
hôte. Ajouter une assertion un-pour-un sur début/fin swap et un budget de
latence. Ne reprendre ni `vsync=false`, ni `Present(0)`, ni un sleep 16 ms comme
politique de cadence.

## XMA, audio et vidéo

Une recherche sur tout l'arbre WIP ne trouve aucune occurrence XMA, XMV ou
Bink. Le code propre au projet ne contient aucun décodeur vidéo/cutscene, aucun
hook de blocs XMA, aucune vérification callback/underrun/EOF/synchronisation
A/V. Il ne fait que régler `audio_maxqframes=10`, laisser les services au SDK
externe et stubber les paramètres de ducker XAudio ainsi que
`XamVoiceSubmitPacket` ([stubs][bo2-stubs]).

Classement : **`documented-unmatched`** pour BO2 et au mieux
`provisional-rexglue` pour les services génériques non verrouillés. Aucun
élément n'est promu vers AC6. Il faut des tests AC6 bornés et indépendants pour
blocs/décodeur XMA, ordre des callbacks, pression/underrun de queue, puis
ouverture/décodage/EOF vidéo et dérive A/V. Conserver
`SDL_AUDIODRIVER=dummy` dans le harnais headless AC6.

## VFS, contenu, sauvegardes et changement de XEX

Le résolveur cherche jusqu'à huit ancêtres et accepte le premier fichier nommé
`assets/<xex>` ou `<xex>`, sans identité ni hash, puis aliase
`update_data_root` au même répertoire ([résolution][bo2-project-paths]). Cela
peut sélectionner silencieusement un mauvais dump/TU. Les énumérateurs
`XamContent*` échouent alors que `XamContentInstall` est un stub succès
([stubs][bo2-stubs]). Aucun code/test ne couvre montage de contenu,
normalisation/casse/traversal, quota, création/écriture/flush/rename/reopen ou
récupération de sauvegarde.

Le passage SP↔MP/Zombies n'émule pas un chargement titre retail : il inspecte le
chemin et un octet de launch data, puis lance un autre processus Windows ;
Android transmet un fichier cache et peut synthétiser quatre octets
([handoff][bo2-title-handoff]). C'est **`divergent`**, mais cela rappelle de
capturer exactement chemin, taille et octets de launch data.

Action AC6 : refuser toute découverte au nom seul ; sceller projet Ghidra,
module, PAL `default.xex` et SHA-256. Ajouter des tests VFS de casse,
normalisation et rejet de traversal, puis une transaction de sauvegarde
create→write→flush→rename→reopen, quota/erreur et corruption. Un boot ne vaut
pas validation content/save.

## Renderer, Xenos et EDRAM

### Ce qui est transférable comme instrument

Le WIP définit des callbacks packet/draw/shader/constants/swap, capture index,
vertex/texture fetch, constantes, état de rendu, début/fin de frame et
ressources latérales. Le writer sérialise sous mutex avec un `seq` croissant
([writer][bo2-capture-writer]) et borne certains payloads
([structures][bo2-render-types]). Les diagnostics exposent notamment draws
tentés/soumis/ignorés/no-op, motifs non supportés, PSO cache, frame
présentable/retenue. Cette forme de télémétrie, après réimplémentation sur un
ReXGlue public et verrouillé, est **`provisional-rexglue`** et peut durcir le
harnais AC6.

Il faut toutefois ajouter au format AC6 : version de schéma, SHA-256 XEX et
module, tick/thread guest, endianness explicite, hash BLAKE3/SHA-256 de chaque
sidecar, longueur demandée/capturée, marqueur de troncature, validation stricte
de monotonie/unicité des séquences et manifeste final atomique. Ici, les
sidecars ne stockent que chemin et `byte_count`
([écriture sidecar][bo2-sidecars]). Le loader exige seulement un `seq` non nul,
parse le JSONL et charge les sidecars ([parse][bo2-replay-parse]); il vérifie
des tailles et quelques manques d'index/vertex, mais ni digest, ni identité
binaire, ni ordre monotone, ni fidélité visuelle. « Validation OK » signifie
donc cohérence de ce schéma, pas parité retail
([sortie validation][bo2-validation-ok]).

### Pourquoi le renderer reste divergent

L'état capturé inclut les registres `rb_copy_*` et clear EDRAM
([état EDRAM][bo2-render-types]), mais le backend D3D12 reconstruit des copies,
formats et profondeur hôte de façon partielle, tandis que le traducteur DXBC
désactive EDRAM ROV. Le choix de surface présentée est un score heuristique
selon les draws de scène ([sélection][bo2-present-choice]). Après la première
image retenue, le dépôt exige seulement 12 draws de scène et 50 % de couverture,
sinon conserve l'ancienne image. Sa propre documentation décrit menu MP
partiellement correct, UI/texte incomplets, flicker/noir et ce seuil comme un
garde de stabilité, pas un achèvement
([limites][bo2-render-limits]). Ce renderer est **`divergent`** et ne doit pas
être porté dans AC6.

Le harnais de régression déclare 14 cas validation/replay/précompilation et
compare métriques plus SHA-256 de BMP ([cas][bo2-regression-cases],
[exécution][bo2-regression-run]). Mais ses quatre captures
`native_captures/.../events.jsonl` et ses exécutables Windows ne sont pas
versionnés. Trois cas « real » distincts partagent le même hash BMP dans les
goldens ([goldens][bo2-goldens]), ce qui détecte une dérive technique mais ne
constitue pas trois références visuelles de scènes. Aucun CI n'exécute le
harnais. Tous ses résultats restent **`documented-unmatched`**.

## Linux, tests, packaging et licences

`main` dit explicitement Linux « Untested / Unsupported »
([README][bo2-readme-platforms]). Le WIP ajoute des presets AMD64/ARM64/Android,
mais :

- le CMake applique `-mssse3` à `rexcore` pour Clang/GNU sans garde
  d'architecture ([CMake][bo2-cmake-ssse3]), en contradiction avec ses presets
  ARM64 ([presets][bo2-presets-arm64]) ;
- le hook d'entrée retourne avant installation sous Linux ; D3D12 live et le
  pont XenosRecomp sont Windows-only ;
- `build_and_setup.sh` ne fabrique aucun paquet : il copie uniquement
  `default`/`default_mp` dans `out/` ([build Linux][bo2-linux-build]) ;
- `scripts/linux/build_android.sh` est suivi avec CRLF et échoue à `bash -n` à
  la définition de la première fonction ;
- il n'existe ni CI, archive/AppImage, bundle de bibliothèques, vérification
  RPATH, signature, SBOM, NOTICE, ni release ;
- `package-lock.json` verrouille seulement `xxhash-addon` 2.1.0 et son intégrité,
  mais `package.json` n'a aucune commande `test`
  ([outils Node][bo2-package-json]).

Le dépôt racine n'a ni `LICENSE`, ni `COPYING`, ni `NOTICE`, et l'API GitHub ne
détecte aucune licence. L'absence de licence interdit de réutiliser son code
dans AC6 sans autorisation. Les caches shaders rendent aussi leur provenance à
clarifier. Pour AC6 : CI Linux de configure/build/package à froid sur pins
publics, smoke headless sans retail (puis validation retail locale bornée),
`SDL_AUDIODRIVER=dummy`, contrôle RPATH/dépendances, manifeste de licences et
SBOM. Ne reprendre aucun preset ARM avant correction des options ISA.

## Synthèse taxonomique et actions AC6

| Élément BO2 | Classe | Décision AC6 |
|---|---|---|
| runtime `main`, boot/jouabilité | `documented-unmatched` | aucune promotion : XEX et SDK non qualifiés, aucune preuve suivie |
| services génériques du SDK externe | `provisional-rexglue` | seulement comme piste ; qualifier un SHA public et des tests AC6 |
| seam CP/VdSwap, schéma de trace et compteurs | `provisional-rexglue` | réimplémenter avec identité, digests, temps guest et validation stricte |
| injection clavier/souris et hook `XamInputGetState` | `divergent` | ne pas porter ; construire capture/replay exact au bord XAM AC6 |
| `vsync=false`, `Present(0)`, sleep 16 ms, benchmark moyen | `divergent` | séparer tick/poll/swap/present et préserver le writeback guest |
| D3D12 partiel, choix de RT/seuil de couverture, EDRAM simplifié | `divergent` | instrumentation uniquement ; Xenos/XenosRecomp AC6 reste qualifié séparément |
| captures/goldens et gameplay WIP | `documented-unmatched` | fixtures absentes : aucune valeur de référence |
| XMA/vidéo, VFS/content/save, Linux/package | `documented-unmatched` | ouvrir des gates AC6 dédiées ; ne pas déduire de la jouabilité BO2 |
| preuve retail qualifiée | **aucune** | zéro promotion `retail-qualified` |

Ordre recommandé pour Mission 01 :

1. **P0 input/cadence** — trace/replay de chaque poll XAM et de chaque
   VdSwap/writeback avec ordinal, thread et tick guest ; test de polls multiples
   par tick et d'absence de dépendance au present hôte.
2. **P0 capture renderer** — format versionné, XEX SHA-256, séquence stricte,
   sidecars digestés, compteurs pertes/troncatures et fixture synthétique ; le
   hook reste observation-only et laisse la commande Xenos originale s'exécuter.
3. **P0 VFS/save** — racines explicites, aucun scan au nom, matrice
   casse/traversal/erreurs et transaction de sauvegarde atomique/récupérable.
4. **P1 média** — gates XMA et vidéo séparées avec callbacks, underruns, EOF et
   dérive A/V ; aucune promotion sur un simple boot.
5. **P1 Linux/package** — build froid reproductible, smoke Xvfb + audio dummy,
   archive contrôlée, RPATH, licences/SBOM et hashes d'artefacts.

## Validations effectuées et risques résiduels

- Métadonnées GitHub API vérifiées le 2026-08-12 : deux branches ci-dessus,
  zéro tag/release/fork/PR/workflow et aucune licence détectée.
- `git fsck --full --no-dangling` : OK sur les clones BO2 et ReXGlue.
- Arbres/parents/comptages, gitlink XenosRecomp et cinq gitlinks imbriqués
  vérifiés par objets Git/API.
- `node --check` : 16/16 fichiers `.mjs` OK ; JSON : `package.json`, lock,
  deux `CMakePresets.json` et `goldens.json` OK.
- `bash -n` : 3/4 scripts Linux OK ; `build_android.sh` échoue sur ses CRLF.
- Recherche statique complète : aucun XMA/XMV/Bink, aucun XenonRecomp,
  XenonAnalyse ou rexdex ; callbacks renderer absents des quatre états ReXGlue
  publics vérifiés.
- Aucun build n'a été revendiqué : code généré, SDK privé et fixtures manquent.
  Aucun binaire de jeu ou runtime n'a été lancé.

Risques restants : la branche WIP est non fusionnée et peut disparaître ; un SDK
ReXGlue local inédit et les captures privées peuvent contenir des corrections
ou preuves non auditables ; l'absence de SHA-256 XEX empêche toute attribution
des adresses ; les shaders suivis ont une provenance/licence non documentée ;
les observations BO2 restent spécifiques au titre et ne prouvent aucune
équivalence AC6/Xenos.
